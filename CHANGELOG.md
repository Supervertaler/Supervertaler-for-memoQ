# Changelog

Supervertaler for memoQ is pre-release: nothing below has shipped to anyone yet.
This first entry summarises what exists today; from here on, every change to
user-visible behaviour gets a line in the same commit that makes it. The shape
matches the Supervertaler for Trados changelog – one bold headline per bullet,
a ★ on the things a release would be announced for – so the two read alike and
any release tooling that buckets on these headings works for both.

## [Unreleased] – 2026-09-16

### Changed

- **Two things were called Settings.** The editor has a Settings menu and a Settings button on its toolbar, and they led to different places, so the first person looking for the licence opened the wrong one. The toolbar button has gone: it opened the same window as **Settings, Translation settings**, and one command in two places read as two different things. Provider, model and key are set once, so the menu is their place; the toolbar keeps what changes while you work. The licence is under **Help**, where people look for one. **Help, Documentation** now opens the front page of the memoQ documentation rather than the page about the prompt editor, which greeted anyone asking for help with the heading “Prompt Library & Editor”.

- **The instructions the AI reads about tags were wrong.** They said tags appear as one fixed form; the first production job contained not one instance of it across 799 rows and used two different forms throughout, with an HTML element arriving as four separate tags. Placeholders are inconsistent too – one kind arrives as a tag, another as ordinary text – so the rule is now to reproduce whatever arrives exactly and assume nothing, rather than to expect a particular shape. The staging instructions also now warn that a paragraph memoQ splits into several rows will match nothing, and describe the two-pass procedure for a large job.

- **The list of staged translations can be paged and filtered.** It returned every pair with both texts on one line, which on a job of 713 pairs was 116,000 characters and overflowed what the caller could read – so the one question it exists to answer, which of my translations did not land, could not be asked of it. It now takes an offset and a limit, a filter for pairs that were never served, a text filter on the source, and a compact form that leaves out the target the caller already knows. It also reports how many there are in total.

- **The live document link ships nothing of memoQ’s.** Its interface assembly is not part of memoQ – it ships inside memoQ’s own PDF Preview tool, a free download from memoQ’s site – and whether it may be redistributed has never been answered, which kept the whole feature on one machine. It is no longer copied into our output at all: memoQ’s PDF Preview tool is a prerequisite, and the link borrows the assembly, and the four libraries that come with it, from wherever that tool installed. Borrowing rather than shipping also guarantees the versions are the ones the interface was built against. If the tool is not installed, the link says so and names the download, and everything else in Supervertaler works as before. This is the same arrangement the add-in already lives under for memoQ’s own libraries.

- **The CS tick now decides how a termbase matches.** Like the AI tick, it was in the Termbases window from the start and nothing read it: every match ignored case. A termbase ticked CS now matches its terms only as written, so an abbreviation stops firing on the same letters inside ordinary words; the rest still match any capitalisation. Where two termbases hold the same term and only one is case-sensitive, each gets its own answer.

- **The AI tick now decides what the model is told.** It was in the Termbases window from the start and nothing read it: every termbase ticked Read reached the prompt. Now Read is what the grid and the terminology pane show you, and AI is what leaves the machine – the terms in a batch or single-segment prompt, the hits AutoPrompt draws on, the pairs the Claude tools read – and a termbase ticked Read without AI stays on your screen and goes no further. Which is what the two ticks always claimed.

- **A term added by the Claude tools goes into the project termbase.** `add_term` over the bridge used to append a line to the glossary file. It now writes to whichever termbase is ticked both Read and Project for the current memoQ project, and says which; with none ticked it says so rather than guessing at a background termbase.

### Removed

- **The text glossaries.** The tab-separated files in `memoq\glossaries`, the Glossaries folder in the editor's tree with its own grid, the Glossary row in the context bar, the terminology plugin's own options dialog, and the *Choose the active glossary* and *Export … as a glossary* commands are gone. They were the terminology system before the termbases existed, and keeping both meant two editors, two sources and two places a term could live. Everything they did the termbases now do: your three files have been imported as termbases (and left where they were), **Termbase from this prompt's terms…** replaces *Export glossary* and makes the result the project's termbase, and the terminology plugin's Options button opens the prompt editor, where the Termbases window is. Import… still reads the old file format, so a glossary from anywhere else becomes a termbase in one click.

### Fixed

- **Every row you landed on paid full price for the whole prompt and memory bank.** Pre-translate has used prompt caching for weeks, but the request memoQ makes when you move to a row never asked for it – so with a 26,000-token memory bank each row sent about 41,000 input tokens at the full rate, and an ordinary morning of work in memoQ cost several dollars on Opus. It now asks, and because the prompt and bank are the same text for every row of a job, each row after the first reads them back at a tenth of the price. The Activity window shows a Tokens line for each such request; *cached* should appear from the second row on.

- **A note from the model could land in the target text.** On a live job the model appended an English remark to a Dutch translation – in markdown, addressed to the translator, explaining a choice it had made against the translation memory – and it went into the grid as part of the translation. memoQ has no base prompt of its own, so what a reply could contain was whatever the selected prompt happened to say, and the default prompt said nothing firm. Every request now ends with a fixed output contract, whichever prompt is selected: the translation and nothing else, tags reproduced exactly, and anything worth flagging in one `[[TC: …]]` marker at the end of the segment, written to the client. And every reply is checked before it reaches the grid. One that carries commentary – a note after the translation, the model writing about its own choices, markdown or a line break the source does not have, more than one marker – is asked for again with the contract restated, and a second offence is not written at all: the row is left for you, and memoQ shows under it why, with what the model sent. The Activity window shows each retry and refusal. Tags that differ from the source are reported there but not refused, since a dropped formatting tag is often right.

- **Rows holding only a tag came back empty.** A segment whose source is a single placeholder – a product name, a variable – has no text, and both translation paths treated no text as nothing there and answered with an empty translation, which memoQ duly wrote in, deleting the tag. On one job five rows lost their placeholder this way while their neighbours were filled correctly. A row with only tags, spaces or punctuation now gets its own source back, tags intact and in order, and no model is asked.

- **You can see which rows the model wrote.** After Pre-translate, staged translations and the model's look the same in the grid. The Activity window now has a Rows line for every call – how many were staged, how many the model wrote, how many were copied because there was nothing to translate, and how many were left for you – and adds them up across the run.

- **The Default Translation Prompt no longer asks for explanations.** It told the model to keep a term with no established equivalent "and add a brief explanation in parentheses if needed" – which is how a note ended up in a target. It now says to keep the term and flag it with a `[[TC: …]]` marker if it needs flagging. Your copy is updated the first time the new version starts, but only if it is still the shipped default; a copy you have edited is left exactly as it is. The prompt library is shared, so this applies in Supervertaler for Trados too.

- **Editing a built-in prompt saves a copy.** The editor let you change the Default Translation Prompt, or any built-in prompt, and saved the change over the shipped file – which the next update of that prompt would then have replaced, taking your work with it. Your changes are now saved as a prompt of your own, "… (my version)" unless you rename it, which memoQ uses from then on if the original was the active prompt. The built-in one is left as it shipped.

- **A memory bank could be filed against the previous client’s project.** The editor showed whichever project memoQ last reported, and until memoQ’s first request of a session – no segment clicked into yet, or a project whose manager has switched MT plugins off – that was yesterday’s project, shown exactly as if it were open now. A bank chosen at that moment was remembered for the wrong job. The editor now knows which memoQ session reported the project: until the running memoQ has said so itself, the heading says **(earlier memoQ session)** in amber, and so does the memory bank chooser, before you choose rather than after. It does not refuse – filing a bank against the previous project can be exactly what you mean – but it is no longer silent. The Activity window notes the moment the project becomes current. The chooser’s own caption was also being cut to its first line, which is fixed. (#8)

- **The swap button in the Add term dialog was an empty box.** It was drawn as an arrow character that the font memoQ uses does not have, so nothing appeared – and because the button was sized from that same character, it collapsed to a narrow blank square between the two term fields. It says **Swap** now, and the gap between the fields is measured from the button rather than the other way round. Three more things in that dialog were wrong underneath it and are fixed too: the line naming the termbase sat on top of the Add and Cancel buttons, the language headings overlapped the boxes below them, and every button was two pixels shorter than its own text. The same two-pixel fault, and a clipped language name, are fixed in the New termbase dialog.

- **Asking an AI assistant what it can do in memoQ got an answer a fortnight out of date.** The card it shows had been written before the live document link, the quality checks and the termbases existed, so it still said the cursor could not be moved and that terms were added to a glossary that no longer exists. It now covers navigation, the checks over the live document, the termbases, verifying which staged translations landed, and the memory banks – and the list of what Supervertaler cannot do names only things it genuinely cannot do: type into the grid, confirm a segment, or read memoQ’s own translation memories. A test now fails the build when a tool exists that the card does not mention, or when the card claims it cannot do something a tool plainly does.

- **The Add term dialog clipped its buttons and its warning, and the swap arrow sat on top of the Dutch box.** Same cause as the other two dialogs: sizes written as numbers rather than measured. On this machine Add and Cancel need 28 pixels of height and were given 26, and the arrow needs 75 of width and was given 28. Everything is measured now, and the warning wraps instead of being cut off mid-sentence. The wording was also unhelpful – it described what had happened rather than what to do – and now leads with "Check these are the right way round".

- **Alt+Up could put a term in backwards, and said nothing.** When neither word could be placed – because the English term appeared in the target as well as the source, and the Dutch one had just been typed and had not reached the live view – the plugin fell back on the order the keys were pressed in and assumed the source came first. Working target-first therefore produced a reversed pair, which matches nothing ever again and looks exactly like a term that is simply never used.

  The two uncertain cases are no longer treated alike. A word appearing on **both** sides is still a word of the source. A word appearing on **neither** means the live view has not caught up with the cell being edited, and that cell is the target. Where the order still has to be inferred, the dialog now says so in red and a swap button puts the pair the other way round in one click.

- **Buttons were cut off, and a long caption ran off the edge, in the New termbase and New memory bank dialogs.** Both set a fixed size and placed their buttons a fixed distance up from the bottom without saying how tall a button is – so at a larger interface font the buttons grew past the edge they had been measured against. The caption was a label that could not wrap, so a sentence longer than the dialog simply disappeared off the right. Both dialogs are now as tall as their contents turn out to be, captions wrap, and buttons are as wide and as tall as their text needs. A test now builds each dialog and measures whether anything sticks out past its own edge, at whatever font the machine is set to.

- **A trailing space was doubled.** memoQ appends the source’s trailing whitespace to whatever a translation provider returns, so a staged target that already carried it arrived in the grid with it twice – which memoQ’s own QA then flagged. Staged targets now have their trailing whitespace matched to the source, and the reply says how many were adjusted.

- **Pre-translate emptied every row it had no staged translation for.** With "Pre-translate only captures and delivers staged translations" switched on, any row Claude had not staged came back as an empty translation – and memoQ does what it is told, so the target was cleared. A fuzzy match, an earlier pass or a human’s own work was silently replaced by nothing. Found on a production job where 32 rows came back blank, every one of which had content before the run. Such a row is now reported to memoQ as having no result, which is what the plugin interface provides for that, and memoQ leaves the target exactly as it was and says so under the grid.

- **Staging said nothing when a source matched nothing.** Translations are staged against the source text character for character, so one wrong character means a pair that can never fire – and the reply was a cheerful count with no hint that some of them corresponded to no segment in the project. On the same job four pairs were staged against a source with one Chinese character mistyped, and those rows would have shipped untranslated behind a clean confirmation. Staging now names the sources that match nothing it has seen. Non-ASCII text, curly quotation marks and trailing spaces are where this happens.

- **A prompt row listing alternatives became one term that could never match, and lost the other.** A locked-terms row is meant to carry one source and one binding target, so a cell holding "a / b" is the model disobeying – but the handling for it collapsed the target to its first alternative before anything looked at the source. "inrichting / werkwijze | device / method" became a single term whose source was the literal text with the slash in it, matching nothing ever, with the second rendering surviving only inside a note. The three cases are now told apart: both sides listed and matching, pair them; several sources and one target, each source renders that way; one source and several renderings, the first is binding and the rest recorded. A "never use" note now bans the rendering for every term the row produced rather than the first.

- **A termbase made from a prompt lost the notes column.** A locked-terms table’s third column is the only part that says why a term was chosen – "only in the claims", "never in this sense" – and the termbase kept the decision while dropping the reasoning, which is the half that ages worst. The note now travels into every row, including both halves when a pair splits and the forbidden row that a "never use" note generates.

- **A term with an invisible character in it could never be found again.** A term picked up from a segment carries that segment’s invisible characters, and a zero-width space – which documents converted from InDesign are full of – survives everything: it is not whitespace, so trimming leaves it, and it cannot be folded away at match time because folding must not change a length. So the term was stored dead, for this product and for Supervertaler for Trados alike, with nothing on screen to explain it. Terms are now cleaned as they are written: every kind of space stored as an ordinary one, runs collapsed, zero-width characters removed. The Alt+Up shortcut made this easy to hit, since it takes a term straight from a segment. Reported by the Trados side, which has cleaned its own writes for longer.

- **Terms containing a no-break space or a smart apostrophe were invisible across products.** Supervertaler for Trados folds both to their ordinary forms before matching and has done for far longer than it has folded subscripts; this product’s first pass at a shared fold took only the chemical characters. A term saved in Trados with a smart apostrophe therefore could not be found here, in the same termbase, with no error – and apostrophes and no-break spaces are far commoner in this work than any formula. The two lists are now adopted from that side exactly, by code point. The user’s own spelling is untouched in the pane, the prompt and any export; only matching folds.

- **A chemical formula is matched however it was written, and a term is no longer found inside one.** Subscripts and superscripts reach the shared termbase in two shapes: Supervertaler for Trados converts sub- and superscript formatting to real Unicode when a term is saved, so it stores ClO₃⁻, while memoQ reads a selection as plain text and stores ClO3-. Both are now folded to the same form when a term is indexed and when a segment is read, so a term saved in either product is found in the other – without it, terms saved in Trados were silently invisible here, in the same termbase, with nothing to see. The fold also fixes a wrong match: to .NET a subscript digit is neither a letter nor a digit, so the boundary test saw nothing either side of the O in H₂O₂ and a one-letter term was accepted as a word of its own inside the formula. The character list is agreed with Supervertaler for Trados and covered by a test on both sides.

- **The first Alt+Up of a memoQ session said no word was selected when one was.** Only the first: the thread handling the press is new, the clipboard has not been touched from memoQ’s process yet, and memoQ builds several formats for one copied word, so the answer to the first Ctrl+C arrived after the plugin had stopped waiting for it. It now waits longer and asks a second time before concluding anything, and the log says which of the three things happened – no answer at all, an answer carrying no text, or a blank selection – because to the user those are one message and to us they are three different faults.

- **The Termbases row in the context bar began with an ellipsis.** The rows are shortened, when they have to be, by dropping the project name that is written just above them – right for a prompt or a bank named after the project, wrong for this row, where the project termbase is named after the project too and the line came out as “… (project) + 2 background”, naming no termbase at all. The name is what the row is for, so it is now the last thing to go: the row first drops “background”, then “(project)”, then shortens “to the model”, and only when even that will not fit does it cut – from the middle, so the name still starts the line. The full line is on the tooltip as before.

- **The Termbases table clipped its own column headings.** The header row and the rows below it were left at the sizes WinForms chooses for a font this program stopped using, so every heading sat a pixel or two short. They are now measured from the font actually in use, and the Termbase column stretches to the right-hand edge instead of leaving a band of empty grid beside Languages.

- **A termbase stored the other way round was silently dead.** Nineteen of the eighty-four termbases here are stored English to Dutch while the work is Dutch to English, and memoQ was searching only the source side of each one – so those nineteen were being asked to find English words in Dutch text, and found almost nothing. It was the quietest possible failure: a termbase with no matches looks exactly like a termbase with nothing relevant in it. The one word that did come through was “water”, which is spelled the same in both languages and so appears on both sides. A termbase whose languages are the reverse of the job is now turned round as it is read, as Supervertaler for Trados does; one already the right way round is untouched, and one in an unrelated language pair is read as stored rather than quietly dropped.

- **The terminology provider hid itself unless a glossary file was set.** It reported itself to memoQ as unconfigured whenever the Glossary box said none – so a project with termbases selected and no glossary was never even offered **Supervertaler terms** in its list of term bases, and the terms sat loaded and ready with no way to reach the grid. Termbases now count as configuration in their own right.

- **Termbases are read through the same SQLite library Supervertaler for Trados uses.** memoQ ships two, and the one this used until now cannot handle full-text search at all – it could not read the search indexes already in the shared file, and could not have built that file from scratch for someone who has never installed Supervertaler for Trados or Workbench. Nothing extra is installed either way: both libraries are memoQ's own copies, used where they lie, and memoQ's own termbase engine is built on the one now in use. Reading every term in the file went from 217 ms to 101 ms in passing.

- **Termbases… opened on an error instead of a list.** The prompt editor is a separate program from the plugin, and it borrows its SQLite library from memoQ rather than carrying one of its own – but it is installed one directory below the library, in memoQ's Addins folder, and a program does not look for a library above itself. So every other pane worked and that one dialog could not open. The editor now looks for what it borrows in memoQ's own directory. The plugin inside memoQ was never affected, which is why the test harnesses did not catch it: each one installs a search path of its own before loading anything, so they were testing a condition the real program never runs in.

### Added

- ★ **A free trial, and one licence for both Supervertaler products.** The same licence now covers Supervertaler for Trados and Supervertaler for memoQ, so a translator who owns one does not buy again for the other, and a key already activated on a computer in Trados is recognised in memoQ without using a second activation. **Help, Licence…** in the editor shows where things stand – the trial’s days left, the key, when it was last confirmed – and is where a key is entered. Only a licence known to have lapsed pauses anything, and what pauses is the AI: translation, the tools Claude and ChatGPT use, and AutoPrompt. Terminology, termbases, prompts and memory banks always keep working, because they are your own work. And if the licence cannot be read at all, everything keeps working: a missing answer is never treated as a refusal. When the AI is paused, memoQ says why under the grid and the assistants say why in the chat, with the one step that fixes it – a key for a trial that has ended, a connection for a licence that has not been confirmed for 30 days.

- ★ **One button per assistant, and nothing to download or find.** The Claude Desktop extension now ships inside the installer, and **Settings, Connect AI assistant…** has a button for each. The ChatGPT one does the whole job. The Claude one shows you the extension and copies its location, because Claude Desktop installs extensions from inside its own settings and nothing outside it can do that step for you – paste the location into Claude’s file box and it is two clicks. Neither asks you to go and find a file. The documentation route is still there, under the button, for anyone who would rather do it by hand.

- ★ **ChatGPT desktop can drive memoQ too, and the editor sets it up for you.** Until now the live connection was Claude Desktop only. ChatGPT has no equivalent of Claude’s one-click extension – its own bundles go through a marketplace, which is more work rather than less – so the editor does the work instead: **Settings, Connect AI assistant…** downloads the Supervertaler MCP server, keeps it in your Supervertaler data folder and registers it, with no file to unpack and nothing to edit by hand. Quit ChatGPT from the notification area afterwards – closing the window is not enough – then start it again and ask it what memoQ project is open. The same entry also serves the Codex command line and the Codex editor extension. If you use Supervertaler for Trados as well, both are registered side by side and each assistant reaches its own CAT tool. What cannot work is an assistant that runs the server in the cloud, which includes the claude.ai and chatgpt.com **websites** as opposed to the desktop apps – the bridge stays on your machine by design, which is why your documents never leave it.

- **An installer.** Until now installing meant copying four files into memoQ’s program folder by hand, with administrator rights, into a path carrying the memoQ version number – so a memoQ upgrade silently broke it. The installer finds whichever memoQ is present rather than assuming a version, refuses politely if memoQ is running instead of failing with a file-lock error, places the add-in and the prompt editor where memoQ looks for them, puts the live document link in its own folder, adds a Start Menu entry and registers an uninstaller. The last page now points you at Options, Default resources, MT settings, so Supervertaler is chosen for every new project rather than only the one you have open. It also says, after installing, if memoQ’s PDF Preview tool is missing, because the live document link needs it and would otherwise be quietly absent. Uninstalling removes everything it put there – the add-in, the editor, the live document link, the Start Menu entry – and leaves your own data folder, your prompts, termbases and settings completely alone. It also refuses to uninstall while memoQ is running, because memoQ holds the add-in open and a half-finished removal would leave memoQ still loading a plugin you believe you have removed. Install, uninstall and reinstall all tested. The wizard carries the Supervertaler mark in the memoQ colourway – the vermillion one, not the blue Trados wears – drawn at build time from the same file the rest of the memoQ branding comes from, so it cannot drift. So does the installer itself: its window, its entry in the task bar and the downloaded file in Explorer all show the Supervertaler mark rather than a generic setup icon, at every size Windows asks for.

- **Termbase synonyms are read at last.** Supervertaler for Trados has written and matched them for a long time; this product ignored the table completely, so a synonym saved there was invisible here – in the same termbase, with fewer hits and nothing to say why. There are 1,152 of them in the shared database and 1,086 sit in the one termbase in daily use, which is the worst possible place for a silent gap. Source-side synonyms (397) are now matched, because a term with two spellings genuinely has two things to look for, and a hit on one is labelled **synonym** in the pane so it is clear why a word not in the termbase’s source column matched. Target-side synonyms (755) are shown under the term as *also*, and are never matched on and never sent to the model: the translator may choose between renderings and the model may not. A termbase read the other way round from the job has its two sides swapped, synonyms included.

- **A memory bank can be made from the bank chooser.** There was no way to create one: the chooser listed what already existed, and the only route to a new bank was a link inside the FigureLens images dialog, shown only when a project had none and hidden once it did. So the moment you most want a fresh bank – starting a new job – was the one case with no route to it at all, short of making the folder by hand. The chooser now has a **New memory bank…** button. It suggests the open project’s name, and a name that already exists simply reuses that bank without overwriting anything written in it.

- **A staged translation can name the row it is for**, and the plugin then quotes that row’s source itself. Staging matched on source text alone, which asked the writer to reproduce every string character for character – and a source retyped with one character wrong was accepted and then matched nothing, leaving rows untranslated behind a clean confirmation. Naming the row removes the transcription entirely. It does not help with a paragraph memoQ splits into several rows, and says so.

- **A tool that answers whether the staged translations landed**, over the verification added earlier.

- **Each captured row now says what memoQ’s state for it was**: not started, pre-translated, partially edited, confirmed, proofread, machine translated or rejected. Until now there was no way to tell a row that arrived pre-filled from a row nobody had touched – so when a client asked whether the matched rows had been checked, the honest answer was that the plugin could not say which they were. On the first production job the pre-filled targets were badly wrong and 231 rows of 799 needed changing, which is exactly the population this identifies. memoQ reports the state only on translation requests, so it appears on captured rows and not on the live view.

- **One call that answers "did my translations land".** It compares the live grid against everything staged and reports, per document and in total, how many rows carry the staged translation, how many differ, how many are empty and how many have nothing staged – then lists the problem rows and says in a sentence which of those four things to worry about. Verifying a job previously meant reading every document, reading the staged list and joining the two by hand, three times over, and the staged list was too large to read at all.

- **Staged translations are checked before they are stored.** Tags are compared with the source by the same rule the QA check uses, so a dropped placeholder is reported while the translation is still being handed over rather than after it has reached the translator’s file. Differences are reported, never refused: memoQ’s markup varies by file filter and a difference is not always a mistake.

- **Alt+Up adds a term to the project termbase, from anywhere in memoQ’s grid.** Select a word, press Alt+Up, select its translation, press Alt+Up again, and the quick-add dialog opens with both halves filled in. It is the key Supervertaler for Trados uses for the same thing. Until now the only way in was to select both words, right-click a hit in Translation results and choose Add Selection As Alternative – which works, but is the kind of route nobody finds on their own, and memoQ binds no shortcut to it. memoQ’s own Add Term button and its Ctrl+E cannot help: they offer memoQ’s term bases only. The order does not matter, because the segment itself says which half a word came from: a word in the target text is the translation, whichever press caught it. Where the segment cannot tell – a word spelled the same in both languages, or no live document link to ask – the press order decides. A first press shows what it caught in a small note by the cursor, which takes the focus from nothing, and a second press on the same side replaces that half rather than pairing a word with itself. A half-finished pair is dropped after two minutes and when the project changes, so a word caught in one job can never be written to another job’s termbase. Both this and memoQ’s menu item now run the same code, so a term added either way lands in the same place by the same rules.

- **A switch for it**, in the prompt editor’s Settings menu and in the memoQ settings dialog. It is the one feature that watches the keyboard, so it can be turned off without being uninstalled. The shortcut is swallowed only while memoQ is the window in front and only with Alt held and nothing else, so Alt+Up goes on opening the parent folder in Explorer.

- **A term can be added from memoQ's grid without leaving it.** Select the source word in the source cell and its translation in the target cell, right-click any Supervertaler hit in Translation results and choose **Add Selection As Alternative**: a small Supervertaler dialog opens with both filled in, a Forbidden tick and a note, naming the project termbase it goes into. Press Add and the term is in the grid and the pane within a few seconds, and in Supervertaler for Trados and Workbench at once; a pair the termbase already holds is refused by name, and a termbase that runs the other way round from the project gets the pair turned to fit it. This is the one door memoQ opens for a terminology plugin – its ribbon's Add Term works with memoQ's own term bases only – and the plugin now walks through it: memoQ expects a web address to open and is handed nothing, so the dialog is the whole exchange. With no termbase ticked Project, the dialog says so and where to fix it rather than guessing at a background one.

- **The context bar says which termbases are in force.** Below Model, Prompt and Bank there is now a Termbases row: which termbases are ticked for the project, which of them is the project's, and how many reach the model – "BRANTS (project) + BEIJER · 1 of 2 to the model", or "none" in grey when terminology is off. It is a summary rather than a picker, because a termbase selection is a set and a dropdown cannot hold one; clicking it opens the Termbases window, which can. It keeps itself current when that window closes, when the editor comes back to the front, and when the selection changes underneath it.

- **Terms can be corrected, added and removed one at a time.** **Terms…** in the Termbases window – or a double-click on a termbase – opens its terms in a grid: source, target, a Forbidden tick and notes, with a filter box for the large ones. Type in the empty last row to add a term, edit a cell to correct one, select and remove one; OK writes the lot and Cancel discards it. A pair the termbase already has, either way round, is refused by name and the rest of your edits still go through. The columns are the termbase's own direction, said in the headings – an English-to-Dutch termbase shows English on the left whatever the current job – because this is the one place you see a termbase as it is stored. A change reaches memoQ's grid within a few seconds, without restarting anything, and is found by Supervertaler for Trados and Workbench at once. Definitions, domains and synonyms are deliberately not here: Supervertaler for Trados edits those, and that editor is meant to become shared rather than copied.

- ★ **Termbases can be made, filled, written out and removed from memoQ.** The Termbases window gains **New…**, **Import…**, **Add to…**, **Export…** and **Delete**, which between them are the termbase system a translator who owns neither Supervertaler for Trados nor Workbench was missing. New… makes an empty termbase. Import… makes one from a file – the glossaries the prompt editor has been exporting all along, a memoQ or Excel export, a Trados export – and takes the name and languages from the file's own header, shown for correction before anything is written. Add to… pours a file into an existing termbase, turned round if the file runs the other way, skipping any pair already there in either orientation – the same rule Supervertaler for Trados applies to its own import, so the same file through either product leaves the same termbase. Export… writes a termbase out as a Supervertaler glossary, or as a tab-separated file with a header row for a spreadsheet or for Trados. Delete removes the termbase, its terms and its synonyms – and says so plainly, because the other two products share the file and lose it too. Where there is no database at all yet, New… or Import… creates one, with exactly the schema the other two products create; the test suite checks that against the real file, object by object, so that the two can never quietly disagree. A termbase just made is ticked for the current project as it is made. Measured: 12,000 terms import in under a second.

- **What memoQ writes is what the other two find.** The search index the Workbench uses is now kept current by the database itself, for every product at once: the first time memoQ writes to a file that has no such arrangement it installs it – the same three triggers Supervertaler for Trados installs from its next release, agreed word for word – and rebuilds the index once, so that terms added earlier from any product become findable at the same moment. Until now, no product kept that index up to date on its own: a term added from Trados could not be found in the Workbench, and a term deleted there was still found. Dates, defaults and empty strings are written exactly as Supervertaler for Trados writes them, because the Workbench reads the same columns and an empty string and a missing value are different answers to it.

- **Languages are recognised however they are spelled.** memoQ calls a language “dut-NL”, Trados Studio calls it “nl-NL” and the shared termbase database calls it “nl”, so deciding whether a termbase is in the language a job needs means recognising all three as the same thing. There is now one table for that, shared with Supervertaler for Trados rather than kept here – every ISO language code in both of the usual three-letter forms, the English names, and the handful of old codes still in circulation. A language it does not recognise is left alone rather than guessed at, so an unfamiliar termbase behaves as it did before instead of being mistaken for another language.

- **★ Your termbases now answer in memoQ's grid.** Tick Read on a termbase in **memoQ › Termbases…** and its terms are found in the segments you translate, highlighted in the source and shown in memoQ's own Translation results pane – alongside the glossary file, not instead of it, because a job-specific glossary and a standing termbase are both true at once. Where they overlap the longest match wins, which is already how two glossary entries were settled. A change made in the editor reaches the grid within a few seconds; memoQ does not need restarting.

- **One termbase is the project’s; the rest are background.** That is the whole distinction, and it is the one Supervertaler for Trados makes: a small, deliberate termbase for the job in hand, against any number of standing ones. Its hits are shaded darker in the source and the pane names it as the project termbase, so a project term is recognisable without reading anything. Only one termbase can hold it – ticking a second releases the first – and whichever one Supervertaler for Trados already treats as the project termbase is the starting answer here, so it need not be nominated twice. Sending a termbase to the AI stays a separate tick, because the two decisions are separate.

- **The termbases you already keep in Supervertaler for Trados are visible to memoQ.** **memoQ › Termbases…** in the prompt editor lists every termbase in the database that Supervertaler for Trados and Supervertaler Workbench share – 84 of them here, 36,000 terms – with four things memoQ decides for itself: whether to consult it in this project, whether it is the project termbase, whether to match case-sensitively, and whether its terms reach the model. The database is opened read-only and is never written to, so Trados's and Workbench's own settings are untouched; memoQ's answers live in their own file beside the glossaries. Nothing is selected until you select it.

- **The window takes memoQ's own scheme.** The toolbar, the menu, the band at the top and the ground behind them are a pale blue-grey rather than Windows' default control grey, while the library tree and the editor stay white. That is what memoQ does with its own frame, and it is why its dashboard does not read as grey although almost all of it is neutral. Under a high-contrast or dark Windows theme the tint is not used and the system colour is, so the chrome stays readable.

- **The thing in use is the one thing with colour.** The prompt, glossary and memory bank currently in force are drawn in memoQ's vermillion in the library tree, so “which one is live?” is answered by looking rather than by reading, and they are bold as well so the colour is never the only signal. It is the only colour in the window and it means only that. The shade is the brand colour darkened to 5.1:1 on white – memoQ's own #F05137 is 3.5:1 and fails as text.

- **The editing pane says when nothing is open in it.** Selecting a folder – which is what the window opens on – left the largest surface in the program blank white, under an empty Name and Description. It now says what to do instead, and the fields and the editor are hidden rather than shown empty: an empty Name box invites you to type into it, and typing there does nothing when no prompt is loaded.

- **The prompt editor stops looking like it was built in 1998.** Nothing in it ever set a font, so it inherited WinForms' own default – Microsoft Sans Serif 8.25pt – while everything around it used Segoe UI. Every window now takes the font the shell uses for its own dialogs, which also means it follows a larger UI font if you have set one. The library tree loses the dotted connector lines, gains room between rows and highlights the row under the pointer. And the four rows that say what memoQ will use next – model, prompt, glossary, bank – are each one bordered field with the chevron inside it, instead of a label, some loose text and an arrow pushed to the far side of the panel with nothing in between. The caption is now the grey one: captions were black and values grey, which said the value was the unavailable half.

- **A refused AutoPrompt draft says why, when the provider says why.** Every model reports why it stopped writing – finished, hit its output limit, refused on content – and that field was being thrown away, which is how a cut-off prompt can leave no evidence of its own cause. It is now kept, in the provider's own words, and a refusal reads “the provider reported that the model hit its output limit” instead of describing the symptom. A stop reason that is not a limit is not reported as one: the wrong cause sends you to the wrong setting. The draft is also checked against the list of sections the request actually asked for, so a prompt missing a run of sections off the end is refused by name. Shared with Supervertaler for Trados.

- **A cut-off AutoPrompt draft is refused instead of saved.** A model's answer that begins the prompt and never ends it is truncated, and the draft used to fall through to the whole raw answer – delimiter line and all – with nothing said. That is how a prompt missing a third of its glossary can be used to translate a whole document. A start without an end is now an error, and the draft is checked before it is handed back: a prompt with no output-format section, a heading with nothing under it, a glossary row that stops mid-cell, or numbering with a hole in it is reported and not saved, with the reason named and “press Generate again”. An answer carrying no delimiters at all is still accepted, because some models ignore the instruction and return a perfectly good prompt. The checks are shared with Supervertaler for Trados. One shape still gets through, and is written down in the test rather than glossed over: a cut inside the body of the final section, after the output-format section already exists.

- **A batch no longer tells the model to skip the segments it must translate.** When memoQ forwards its best fuzzy TM match for a row, that match is shown to the model as an approved translation for a nearly identical source. The block introducing those matches ended – wrongly, here – with “these are reference only, do not return a translation for them”, wording that suits a tool sending matches for surrounding segments. In memoQ the matches belong to the very rows being translated, so the prompt asked the model to skip work it was simultaneously demanding. It now says the opposite in as many words. Whether any model actually acted on the contradiction is unmeasured; a batch that came back short was already reported rather than silently misaligned. Shared with Supervertaler for Trados.

- ★ **An AI translation engine for memoQ.** Anthropic, OpenAI or Google, with your own API key and your own instructions. Segment-by-segment as you move through the grid, or batched through Pre-translate – memoQ hands the plugin about ten segments at a time, and each batch goes to the model as one numbered request in the format the shared prompt library expects. Inline tags survive the round trip through memoQ's own segment serialiser; a batch that comes back short is reported as the fault it is rather than silently shifting every translation after it. Identical requests are answered from a cache without a second call.
- ★ **It learns from what you confirm.** Every segment you confirm is captured, and the most relevant confirmed pairs are shown to the model when it translates later segments of the same document – your own approved choices fed forward, with no configuration and no retraining. Persisted to disk, so it survives closing memoQ. This uses memoQ's self-learning MT channel, so the engine must also be selected under *Self-learning MT* for capture to begin; the Activity window says when it is not.
- ★ **Translate with Claude Desktop.** The plugin hosts a bridge for the Supervertaler MCP Server, so Claude – or any local MCP client – can read the document you are translating, your confirmed segments, your glossary and your memory banks, and *stage* translations that flow into the grid when you press Pre-translate. Tokens go on your Claude subscription rather than an API key, and every write into the document goes through your own hands. Bridge mode is one switch, on the editor's toolbar and in memoQ's dialog, and it is scoped to Pre-translate: suggestions as you move through segments still use the key. Ships as `Supervertaler-for-memoQ-MCP-Server.mcpb` – the same server as the Trados extension with `SUPERVERTALER_HOST=memoq`, wearing the memoQ mark so the two are told apart at a glance in Claude Desktop’s extension list.
- ★ **A live document link.** memoQ's Preview SDK – the interface its own PDF preview uses – is the one channel that shows a tool the target text, the row the cursor is on and the document's real name. `Supervertaler.MemoQ.Preview.exe` registers as a preview tool and forwards that stream to the plugin, so Claude sees the document as it is, can tell which row you are on, and can ask memoQ to jump to a sentence. It draws nothing: it is a link, not a preview. Preview parts are paragraphs, and everything built on them says so.
- ★ **AutoPrompt.** Reads the open document – the live one when the link is connected, otherwise what the plugin has captured – classifies it, and drafts a project-specific translation prompt with a locked-terms table, named after the memoQ project. Confirms the domain with you first, shows exactly what it is about to send, takes a briefing, and greys out any input it has nothing for. A drafted prompt carries the language pair it was drafted for and is marked as drafted, so a machine-written prompt can always be told from a hand-written one.
- ★ **SuperMemory memory banks.** A bank of Markdown articles – brief, terminology, style, and any others – goes to the model with every request, up to a budget, and in full to AutoPrompt. Chosen per project and remembered per project: a job you have never chosen a bank for uses none rather than inheriting the last one, because a bank carries one client's terminology and the wrong one is worse than none. The `_shared` bank travels whether or not a client bank is chosen, and every file at its root reaches the prompt. Banks are served over the bridge too, so Claude can read and search them.
- ★ **A companion window: the prompt editor.** memoQ gives an add-in no window of its own, so everything richer than a settings dialog lives in `Supervertaler.PromptEditor.exe`, launched from memoQ's dialog or pinned to the taskbar. A panel at the top says what memoQ will use for the next segment – project, model, prompt, glossary and memory bank, each on its own row and each changeable there – and the tree beneath it holds what it could use: the prompt library, every memory bank with its articles, and every glossary. Right-click any of the three to make it the active one; the active one is marked in the tree. Prompts and bank articles open in a Markdown editor; a glossary opens as a Source / Target / Forbidden grid, and saving it keeps the file's header and comments where they were.
- ★ **The document’s list numbering reaches the model as structure.** The a), b), c) on the steps of a claim are not text – Word generates them – so neither memoQ’s grid nor anything a plugin receives contains them, and a model shown six unlabelled sentences and then “steps a. to f.” flagged the reference as a possible source defect. The plugin now reads the numbering out of the original `.docx` the preview tool names, counted over the whole document exactly as Word renders it, and sends each paragraph’s marker in front of its first segment as `[#e)]` – declared to the model as structure to use and never to reproduce. Every reply is checked and an echoed marker is removed before it can reach the document, with a line in the Activity window saying so. On by default with no switch; needs the live document link. Shared with Supervertaler for Trados.
- ★ **The pictures in the document reach the model as descriptions.** The AI sees a document's text and not its figures, so a claim that names part 12 is translated by a model that has never seen part 12. **FigureLens…** on the editor's toolbar is the panel for that – named for what it does beside TermLens, which shows the model the terms in a segment where this shows it the pictures. It opens with a table of the project's documents – name in one column, what was found in it in the other – and works in two steps: get the images out of the documents into the memory bank's `figures\` folder, named after their figure numbers – free, no AI – then have each one described, with what the text says about it alongside, and the descriptions saved as `figures.md` in the bank, which every prompt reads. The free alternative describes each figure from the text alone. Drawings placed from CAD or a draughtsman's tool come out of Word as metafiles, which no vision model accepts – these are rasterised on the way out, on a white ground and large enough for thin lines and reference signs to survive, so the figures of a technical document are described rather than refused. A project with several documents holding images gets a folder each – every document numbers its figures from 1, so one folder would mean the second document's "Figure 01" replacing the first's – and every document is written into figures.md, each with its own table. Reference signs the model reads in a drawing that appear nowhere in the text are listed, because that is a defect worth raising before filing. Documents come from the live document link, which names the file memoQ imported: on a local project the original is found without any setting; on a project checked out from a server memoQ records the project manager's path, so the panel says which documents are not on this computer and offers **Locate the original document…** – pointed at the copy you were sent, once, and remembered for that document – and **Add a document file…** for a file memoQ has said nothing about. A document located here also lights up structure context for it. Shared with Supervertaler for Trados.
- **The panel follows the project memoQ is showing.** The plugin used to learn which project was open only from a translation request, so a project that never sent one – MT plugins disabled by the project manager, or simply not clicked into yet – left the editor naming the previous job, and a memory bank chosen then was filed against it. The live document link reports every document memoQ shows, whatever the MT settings say, and a document resolves to its project folder and the project's own GUID (the same one memoQ sends with a request), so the project now switches on the first preview report. The editor re-reads what memoQ wrote every two seconds instead of only when it comes to the front, and the project name is clickable – **Sync with memoQ now** – with a reason in words when it cannot be done.
- **Supervertaler asks memoQ where it keeps its projects.** The projects folder is a setting – *Options → Locations → Projects* – and Supervertaler used to look only in the default `C:\Users\<you>\Documents\My memoQ projects`, so a translator who keeps projects elsewhere was told no project folder held the document. It now reads the custom folder from memoQ's own preferences, keeps the default as well (moving the folder leaves projects in both places), and reads memoQ's register of every project, which names each one's actual folder and carries the same project identifier memoQ sends with a translation request. Rows that outlive the folder they name are skipped rather than believed.
- **Several open documents can be drafted from as one.** A memoQ view merges several files into one editor tab, but memoQ reports each file separately – a three-file view arrives as three documents of 82, 10 and 27 paragraphs, with nothing marking them as one tab – so a prompt drafted for that tab saw one file of the three, and the two small ones are far too thin to classify on their own. AutoPrompt now offers **All 3 documents memoQ is showing** at the top of its list, drafting from every one of them, document by document, each in its own order. The files it covers are the ones listed beneath it. Picking a single file still gives that file alone.
- **AutoPrompt works on a project the plugin is never called for.** The document list offered only what the plugin had captured from translation requests, so on a project whose manager has switched MT plugins off – where nothing is ever captured – there was nothing to choose and no prompt could be drafted, even though the live document link had the whole document. Documents the live link reports are now listed too, counted in paragraphs and marked as coming from it, and the document you pick is the one drafted against rather than whichever is largest.
- **A project checked out from a server is named by its document, not its id.** memoQ stores a local project's documents under folders named after each document's identifier, which is how Supervertaler tells which project a document belongs to. A project checked out from a server stores them under short codes instead, and nothing on disk carries the identifier at all – so such a project could never be named, and the panel said so in a way that blamed the projects folder. The document's own file name is listed in the project file and reported by the live document link, so it is used instead. Two projects holding a file of the same name are left unnamed rather than guessed between: filing a memory bank against the wrong client is worse than naming nothing.
- **The bridge starts when memoQ does.** Everything that reaches Supervertaler from outside memoQ – the prompt editor, the live document link, Claude Desktop – goes through a bridge that only started once memoQ had built a translation engine. A project whose manager has switched MT plugins off, or one where Supervertaler is not the selected engine, never built one, so the editor reported *memoQ appears to have closed* against a memoQ running perfectly well. The bridge now starts with memoQ itself.
- **Terminology in memoQ's own pane.** A tab-separated glossary appears as a memoQ terminology provider – matched terms highlighted in the source, entries rendered in Translation results – and the same terms reach the model. Glossaries declare their language pair, and a glossary facing the wrong way is reported rather than silently matching nothing. **Export glossary** turns a drafted prompt's locked-terms table into a glossary file and makes it active. While a drafted prompt is selected, the glossary's preferred renderings are held back – the prompt's own table is the one authority – but forbidden terms always travel.
- **The short model list.** The model dropdown shows three to five models per provider, each with a one-line verdict, re-judged at release time and shared with Supervertaler for Trados. **Fetch list** asks the provider for its full catalogue and **Show all models** adds it underneath, for a model released after your copy was built. The box stays typeable for a gateway or a local model. Changing the provider changes the model, the list and the API key together.
- **API keys in one file, shared by every Supervertaler product.** `C:\Users\<you>\Supervertaler\settings\api-keys.json` – one key per provider, plain text, editable in Notepad. A key pasted in memoQ, Trados or Sidekick works in all three; a key you had before the file existed is copied in the first time it is needed. The key box says when a key plainly belongs to another service – *this is an OpenAI key, not an Anthropic one* – before the provider refuses it with a 401 that names nothing.
- **Prompt caching, and the numbers to check it by.** The stable half of every batch request – instructions and memory bank – is marked cacheable and identical from batch to batch, so every batch after the first reads it back at a tenth of the input rate; on a measured 370-segment run that turned roughly $10 into roughly $4. The first request of a run goes out alone and warms the cache before the rest go in parallel. Every batch line in the Activity window carries its token counts – regular, cached, written, output – so a saving nobody can see is a saving anybody can check.
- **The Activity window.** memoQ's Pre-translate dialog says only *Processing*. **memoQ → Activity** (Ctrl+L) shows what the plugin is actually doing: the engine and model each project starts with, which bank a project switched to, the glossary as it loads, every batch with its counts and cost, AutoPrompt drafts, the model in force whenever it changes, and anything that failed.
- **QA over the live document.** Numbers, tags, non-breaking spaces, terminology and inconsistencies, checked over the linked document's real target text and served to Claude as tools.
- **Fuzzy matches from memoQ.** When memoQ is set to send its best TM match to the engine, the plugin uses it, and the log says whether one was forwarded.
- **The settings live outside memoQ.** Provider, model, endpoint, prompt, glossary, bank and the rest are in `C:\Users\<you>\AppData\Local\Supervertaler.memoQ\shared.txt`, read by the plugin and the editor alike, so a change in either lands on the next segment and neither needs memoQ's six-click dialog to reach.
- **Documentation** at [docs.supervertaler.com/memoq](https://docs.supervertaler.com/memoq/), including the honest table of which Trados MCP tools do and do not exist for memoQ, and what memoQ's SDKs allow – including the things that fail silently.

### Not yet

- **A term added from the grid appears when you next move onto the segment, not at once.** memoQ asks a terminology plugin about a segment once and keeps the answer, and its terminology SDK has no way to say the answer has changed. The live document link, the one channel that reaches memoQ from outside, can only ask it to select a segment: asked for the range it already had, memoQ accepted and changed nothing; asked for a range it genuinely had to apply, it accepted that too and still did not look the segment up again. So memoQ re-queries terminology when the cursor changes row and not otherwise. Stepping to a neighbouring row and back would work and would cost you your place in the target cell every time you add a term, which is not worth paying when the dialog has already said the term went in.
- A signed build. The installer exists (see Added), but until memoQ has compiled Supervertaler’s public key into one of its own releases, memoQ may warn once that the plugin is unsigned.
- SuperBench (three models, one judge) – shipped in Supervertaler for Trados, tracked for memoQ as #6.
- Word list markers as context for the model, so a lettered list of claim steps is not read as unlabelled sentences – #7, shared with Trados.
